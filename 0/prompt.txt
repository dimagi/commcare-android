#### Important (Should Fix)
1. **`PersonalIdProfileBackupCodeFragment.kt:20,37-43`: `leftForward` is not saved in instance state.**
   - **What's wrong:** Rotation is ruled out (the activity is portrait-locked), but process death and other config changes are not: dark mode, locale, font scale, multi-window. A back-stacked gate is then recreated with `leftForward = false` and is never resumed, because it stays in the back stack. When the "Email added" dialog pops to Profile, the gate's `onDestroy` sees `isRemoving &amp;&amp; !leftForward` and reports cancelled right after success. By then the email is stored, so `ProfileEmailAnalytics` reports it as `email_updated`/`cancelled`, which is the wrong action too.
   - **Why it matters:** The likely trigger is common. The user leaves the app to read the email OTP, and on low-end devices Android may kill the process meanwhile.
   - **How to fix:** Save `leftForward` in `onSaveInstanceState` and restore it in `onCreate`. Add a test that recreates the activity while the user is on Send email OTP, then completes the flow.
2. **Missing test coverage for the analytics seams the spec cares most about.**
   - No test asserts `email_added` (only `email_updated` appears, in the ChangeEmail and SendEmailOtp tests).
   - No test covers success/failure reporting in `PersonalIdProfileEmailVerificationFragment`, including the order relative to `storeUser`.
   - No test shows that the success pop to Profile does not report cancelled, which is the case the `leftForward` flag exists for.
   - No test shows the Forgot?-to-phone route sets `leftForward`.
   - With Ruling 1, the initiated call is untested too.
   - Fix: add these to the existing ChangeEmail and email-verification Robolectric tests. That file set is in scope.

#### Minor (Nice to Have)
1. **`BasePersonalIdPhoneVerificationFragment.kt:206-211`: the auto-switch checks `defaultSmsMethod()`, not the current method.**
   - The spec says "if the current method is not already PersonalID". This is pre-existing Java behaviour.
   - Profile always defaults to Firebase, so a late `onVerificationFailed` from the replaced `FirebaseAuthService` (it still holds `otpCallback`) would send a second PersonalID SMS.
   - Fix: check `lastOtpMethod` instead.
2. **`BasePersonalIdPhoneVerificationFragment.kt:248-252`: the fallback is not sticky.**
   - After an auto-switch, `requestCount` is 2, so the next resend goes back to Firebase. Firebase fails again, and the code switches again.
   - It self-heals, but costs a wasted Firebase call and extra failure events. It matters more in profile, where Firebase is always the default. Pre-existing.
   - Fix: keep PersonalID once `lastOtpMethod == PERSONAL_ID`.
3. **`BasePersonalIdPhoneVerificationFragment.kt:197-199`: every `FAILED_AUTH_ERROR` shows "incorrect OTP".**
   - Under basic auth, a 401 on `send_session_otp` (bad or rotated credentials, or a server not yet deployed) shows "incorrect OTP" before the user has typed anything.
   - The spec asks for this mapping, so the fault is in the plan.
   - Fix: apply the override only when `currentOtpOp == VERIFY_PHONE`.
4. **Asymmetric failure reporting in the email screens.**
   - `BasePersonalIdEmailVerificationFragment`: `onVerifyOtpFailed()` runs after the `hasLiveView()` guard, while Send email OTP reports before its guard.
   - Resend failures on the email verification screen (`requestOtp` failure path) never report failure. The spec's "email OTP send ... failure" arguably covers them.
5. **`PersonalIdProfilePhoneVerificationFragmentTest`: the test "phone verification is popped when moving on to send email otp" launches directly from Profile.**
   - It proves the pop, but not the spec case "back from Send email OTP lands on the backup-code gate".
   - Fix: launch through the gate and assert `personalid_profile_backup_code_fragment`.
6. **`ApiPersonalIdPhoneOtpAuthTest`: `TokenAuth` is only tested for `sendPhoneOtp`.** The spec asks for both auth types on all three calls; `validatePhoneOtp` and `validateFirebaseIdToken` lack `TokenAuth` cases.
7. **`BasePersonalIdPhoneVerificationFragment.kt:330`: pre-existing crash risk.**
   - `onSaveInstanceState` reads `binding` for a signup fragment that was restored in the back stack without a view. In Kotlin that is an `UninitializedPropertyAccessException`; in Java it was an NPE.
   - The profile flow avoids it through `popUpTo`.
   - Fix: keep the verify-enabled state in a field, or guard with `::binding.isInitialized`.
8. **`PersonalIdProfilePhoneVerificationFragment.kt:42`: a null `primaryPhone` would crash.** The Kotlin `PersonalIdAuthService.requestOtp(phoneNumber: String)` would NPE on it. The stored user should always have one, so this is low risk.
